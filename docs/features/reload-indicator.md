# Native weapon reload sweep

Outcome: a real WeaponMechanics reload shades only that weapon's inventory/hotbar icon with Minecraft's native cooldown sweep. No actionbar writer, pack asset, substitute shield, server item edit, real gameplay cooldown or weapon tuning change is added.

## Existing saber pattern and native boundary

The existing `SaberService.stun(Player)` calls `Player.setCooldown(Material.SHIELD, guard(player).stunTicks(tick))`; its guard tick maintains that stun. That deliberately sets both the native visual and a server gameplay lock for shields. Current blasters share `DIAMOND_HOE`, so copying the material-wide setter would affect other guns. `Player.setCooldown(ItemStack, ...)` also creates a real server cooldown; without a custom group it still resolves through the base material.

The matching installed 26.1.2 client was inspected directly. `GuiGraphicsExtractor.itemCooldown` reads `ItemCooldowns.getCooldownPercent` for the item's `USE_COOLDOWN` group. `MultiPlayerGameMode.useItem`/its prediction lambda still constructs and sends `ServerboundUseItemPacket` when the client cooldown returns PASS; `Minecraft.startUseItem` has no earlier cooldown filter. Therefore a client-only group can shade these server-managed blasters while their right-click packets continue reaching WeaponMechanics. Its `ShootHandler.shootWithoutTrigger` cancellation path remains authoritative, including partial reloads and firearm closing. This was also exercised through the actual installed vendor handler during a visible sweep.

`NativeReloadSweep` isolates the pinned Paper 26.1.2 packet boundary. For each accepted reload it installs one temporary outbound-only Netty handler on that player's existing channel. It copies the outgoing item, changes only `USE_COOLDOWN` on that copy to a fresh `mandomc:reload/<uuid>` group, and sends `ClientboundCooldownPacket(group, actualRemainingTicks)`. Server inventory and server cooldown maps are never changed. Other components and current vendor metadata come from the actual outgoing image, rather than an old saved item snapshot.

The projection handles `ClientboundSetPlayerInventoryPacket`, `ClientboundContainerSetSlotPacket` and `ClientboundContainerSetContentPacket`, including player slots in external inventories. Slot plus vendor title identifies the active weapon; an identical same-material weapon in another slot does not acquire the group. Closure first disables projection, clears only its own client group and sends the latest authoritative inventory slot. It then removes the handler. A disconnect/crash cannot persist shadow components because they never existed in server items. Packet projection failures forward the real packet unchanged and disable the observer; gameplay authority is untouched.

## Reload authority and lifecycle

`ReloadIndicator` observes the final `WeaponReloadEvent` at MONITOR, waits for `HandData.isReloading` to confirm actual vendor acceptance, and reads `getReloadCompleteTime` plus `getReloadElapsedTime` capped by elapsed server ticks. Completion and cancellation close the visual immediately. If the client timer expires while the server is still lagging behind, only the remaining actual reload is re-armed; normally progressing sweeps are not continually restarted. Restart acquires a fresh group. Main-hand slot changes, hand swaps, world changes, disconnect, native death and disable clean up the applicable views. Full magazines, vetoed starts and no-ammo rejection never acquire a sweep. All currently reloadable titles use this shared integration; non-reload abilities produce no reload event or artificial cooldown.

## Release and verification

Do not install this branch's entire Maven JAR: the canonical checkout predates several composed deployed features. `scripts/build-reload-overlay.py` compiles only the new integration against an explicitly hash-pinned current release and adds lifecycle calls to the exact deployed bootstrap. Builds use an immutable hash-verified JAR snapshot and reject a baseline that changes during the build. All original lifecycle invocation sequences are verified, while non-lifecycle bootstrap method bytes, fields, class attributes and original constant-pool entries are retained exactly. Every other existing JAR entry remains byte-identical, including the original saber cooldown implementation, Boba equipment/actionbars, combat protection and vendor integrations. Public APIs, redstone agent, launcher and pack remain intact. Before a unified full-source release, invoke `ReloadIndicator.enable/disable` at the same bootstrap boundaries.

`NativeReloadProbe` runs only in a disposable copy of the runtime. It starts actual vendor reload tasks with real generated weapons, routes outgoing native packets through the installed Netty handler, checks the vanilla client cooldown selection/progress algorithm, and verifies completion/ammo/cancellation plus native death and handler cleanup. It checks same-material twins, offhand, restarts, switching, full/no-ammo/veto cases, ordinary and external inventory resyncs, native packet encode/decode and preservation of an existing custom cooldown component/group. The fixture has no third-party join session, so world/logout cleanup callbacks are exercised directly rather than broadcasting fictional cross-plugin sessions. Verification: 107 Java tests; 178 full native assertions; 39 targeted lag/lifecycle assertions; and 39 clean exact-current-baseline startup/native assertions after preserving the latest Boba datapack. Connected-client pixels remain a manual check; no screenshot or visual playtest is claimed by these native assertions.
